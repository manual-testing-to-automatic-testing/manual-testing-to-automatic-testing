# 2.1.1 Describe the Configuration Needs of an Infrastructure that Enable Implementation of Test Automation

Part of [2 Preparing for Test Automation](2-preparing-for-test-automation.md), [2.1 Understand the Configuration of an Infrastructure to Enable Test Automation](2-1-understand-the-configuration-of-an-infrastructure-to-enable-test-automation.md).

**Learning objective:** TAE-2.1.1 (K2).

## In short

Automation needs a **testable** system: one that lets tests see what it is doing (observability), make it do things (controllability), and understand how it is built (architecture transparency). Testability should be designed in from the start.

## Key ideas

**Testability is a non-functional requirement.** It is usually the software architect's job, with a test automation engineer pointing out where it can improve, and it should be built at the same time as the features.

**Ways to make a system easier to automate:**

- **Accessibility identifiers:** stable ids on elements, generated by the framework or set by developers.
- **System environment variables:** application settings that can be changed to make testing easier.
- **Deployment variables:** like environment variables, but set before deployment.

**Three aspects of design for testability:**

- **Observability:** interfaces that show what the SUT is doing, so a test can compare actual and expected results.
- **Controllability:** interfaces that let a test act on the SUT: user interface elements, function calls, protocols, or signals.
- **Architecture transparency:** documentation that shows the components and interfaces clearly, at every test level.

## In this programme

The testingexamples fixture site is designed for testability: every element has a stable id, such as `select-example-1-id`, so tests never depend on page layout. When your team's product lacks ids, ask developers to add them: it is the single biggest improvement to browser automation.

## Teach it (30 minutes)

Open your team's product in the browser's developer tools. Find five elements a test would need. For each, note whether it has a stable id or test id. Write a short request to the developers for the ones that do not.

## Check yourself

1. Who is usually responsible for testability, and when should it be built?
2. Explain observability and controllability, with one example of each.
3. Why do stable element ids make automation more reliable?
